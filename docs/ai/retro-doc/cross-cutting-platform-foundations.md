## What it does

This domain captures three foundations that affect MyAsso across feature areas: localization of the `(main)` application space, tenant-scoped feature-toggle management and environment resolution, and unit-test suite and coverage expectations. The design records place the i18n implementation in `apps/my-asso`, the toggle administration in the same application with supporting APIs and a scheduled Cloud Function, and the coverage configuration in `apps/my-asso` and `apps/api-ae`.

These are design and status records, not a current-code audit. In particular, the i18n status reports say the translation keys and tooling existed while source translation remained incomplete; the toggle records distinguish repository configuration from Firebase deployment; and the coverage initiative reports its 90% target as still open.

## Architecture as designed

- **Localization:** The `(main)` UI uses the existing React `LocaleContext`, `useLocale()` and `t()` pattern with JSON locales at `apps/my-asso/src/i18n/locales/{fr,en,de,es}.json`. French is the source language. Keys are hierarchical and organized around pages and shared categories. A set of extraction, key validation, hardcoded-string detection, coverage and translation scripts supports authoring and CI. `.github/workflows/i18n-check.yml` is the reported CI entry point. The stated feature scope is the 93 TSX files under `src/app/(main)`; admin pages, APIs, generic UI, backend services and user-generated content are outside it.
- **Toggle administration:** `FeatureTogglesContext` uses the Firestore client SDK for application management rather than a REST API. The administration page is `/feature-toggles`, surfaced in the admin sidebar and restricted to users with the `Admin` role. The records describe `feature_toggles` and immutable `feature_toggles_history` collections, Zod validation, group scoping through `authGroupId`, and the `activateScheduledToggles` Cloud Function for scheduled changes. The public toggle endpoint was deferred.
- **Environment-aware toggle state:** Feature 031 extends each toggle document with optional `environments` and `scheduledActivations` maps instead of introducing a separate collection or migrating old documents. A shared `resolveEnvState()` in `apps/my-asso/src/lib/data.ts` is intended for the context, `blog-api`, and Next.js routes. The `blog-api` feature-toggle endpoints and Next.js `/api/feature-toggles/check` and `/api/feature-toggles/list` accept an optional environment. All omit it by default to production. The existing scheduled-toggle function is extended to process environment-specific activations.
- **Coverage:** Jest’s native coverage collection and thresholds are the planned enforcement mechanism. The specified application scopes are `apps/my-asso` and `apps/api-ae`; tests mock Firebase and external services. Coverage is checked when Jest runs with `--coverage`, separately from ordinary test-pass runs. The test-fix effort also spans `blog-api`, `api-juridique`, `api-mail` and `api-event`, but the 90% coverage target is not stated for those projects.

## Invariants

1. Keep the four `(main)` locale files structurally aligned; require non-empty values and matching interpolation variables, and keep nesting at no more than five levels. Add each new key to `fr`, `en`, `de` and `es`, with French as the reference. **Source:** `specs/002-i18n-main-space-translation/spec/plan.md`; `specs/002-i18n-main-space-translation/spec/quickstart.md`; `specs/002-i18n-main-space-translation/spec/research.md`.
2. Use the existing `LocaleContext`/`useLocale()`/`t()` integration for in-scope `(main)` UI; do not introduce another i18n library as part of this design. Keep user-generated content untranslated and RTL support out of scope unless the scope is explicitly revised. **Source:** `specs/002-i18n-main-space-translation/spec/spec.md`; `specs/002-i18n-main-space-translation/spec/plan.md`.
3. Treat translation keys as insufficient evidence that a page is translated: source UI strings must call `t()` as well. Validate key consistency and hardcoded strings, and test language switching in all four locales. **Source:** `specs/002-i18n-main-space-translation/spec/IMPLEMENTATION_PROGRESS.md`; `specs/002-i18n-main-space-translation/spec/quickstart.md`; `specs/002-i18n-main-space-translation/spec/tasks.md`.
4. Scope every toggle operation by `authGroupId`; keep toggle keys unique within a group, validate toggle data with Zod, and preserve immutable history records. **Source:** `specs/025-toggles-management/spec/spec.md`; `specs/025-toggles-management/spec/plan.md`.
5. Restrict toggle administration to `Admin`; do not place the toggle-management system itself behind a feature toggle. **Source:** `specs/025-toggles-management/spec/spec.md`; `specs/025-toggles-management/spec/plan.md`.
6. Resolve supported environment state in this order: explicit `environments.{env}`, legacy `isEnabled`, then `false`. Resolve schedules from `scheduledActivations.{env}`, then the legacy global schedule for `prod`, then immediate activation. **Source:** `specs/031-feature-toggle-env/spec/data-model.md`; `specs/031-feature-toggle-env/spec/spec.md`.
7. Default omitted `env` values to `prod`; reject unsupported environments. Return only the requested environment’s resolved state, not the stored map, and include the evaluated environment in responses. **Source:** `specs/031-feature-toggle-env/spec/contracts/blog-api.md`; `specs/031-feature-toggle-env/spec/contracts/nextjs-api.md`; `specs/031-feature-toggle-env/spec/spec.md`.
8. Never synchronize dev or test state or schedules into legacy `isEnabled`; only production changes may update that compatibility field. Record the affected environment in toggle history. **Source:** `specs/031-feature-toggle-env/spec/data-model.md`; `specs/031-feature-toggle-env/spec/plan.md`; `specs/031-feature-toggle-env/spec/spec.md`.
9. Do not assume existing toggles need migration or backfill; preserve legacy documents and read them through the fallback rules. **Source:** `specs/031-feature-toggle-env/spec/data-model.md`; `specs/031-feature-toggle-env/spec/spec.md`.
10. Keep coverage collection and thresholds aligned with the documented project-specific scopes and exclusions. Mock Firebase and external services in unit tests; keep E2E tests out of Jest coverage. **Source:** `specs/032-unit-tests-coverage/data-model.md`; `specs/032-unit-tests-coverage/plan.md`; `specs/032-unit-tests-coverage/spec/spec.md`.
11. Keep the aggregate Nx test command green, including projects with no test files by adding a test or configuring `passWithNoTests`. Check coverage separately with the project Jest configurations and `--coverage`. **Source:** `specs/032-unit-tests-coverage/spec/spec.md`; `specs/032-unit-tests-coverage/tasks.md`; `specs/032-unit-tests-coverage/plan.md`.

## Drift and superseded decisions

This is the risky part of the document: these records mix specifications, proposed plans and progress reports, and several later records disagree with earlier proposals or with their own checklists. They do not establish what is deployed or what the current code does. Verify the implementation and its tests before relying on any recorded status.

- The February 2026 toggle checklist and post-remediation analysis describe an API-oriented architecture, while the later 19 March specification and plan select Firestore client operations through `FeatureTogglesContext`, make the public API deferred, and locate the route in the admin sidebar. Follow the later design record for intent; check the actual application before changing API or navigation behavior.
- The February toggle implementation status says the feature is complete but lists indexes, rules and the Cloud Function as manual deployment work. The 19 March plan and tasks say indexes, rules and sidebar navigation are in the repository, but Firebase deployment and function deployment remain outstanding. The plan also contradicts itself about whether some configuration and navigation pieces are complete. Do not infer live deployment from checked-in configuration or a “complete” summary.
- Feature 031 is marked “In Progress” in its specification and “Planning” in its plan and tasks; those artifacts do not verify implementation. The specification says no additional composite index is required, research says nested scheduled-date queries may need one, and tasks require a production-schedule index before deployment. Treat scheduled-query index requirements as unresolved and verify the query and deployed index configuration.
- Feature 031’s list-route design fetches a group’s toggles and filters resolved state in JavaScript rather than filtering Firestore by legacy `isEnabled`; its research considers fewer than 100 toggles per association acceptable. Do not reintroduce a stored-field filter that would omit toggles enabled only in another environment.
- Toggle localization status conflicts: the March plan says the management UI was still hardcoded in French, while the later tasks say the four-locale `featureToggles` namespace work is complete. Neither status report establishes the current UI or a passing validation run.
- Earlier toggle design material suggests public REST reads; the later design explicitly defers that endpoint. Do not build consumers against a public toggle endpoint as if it were part of the current contract.
- The i18n reports dated 31 December 2025 describe tooling and 1,608 keys as prepared, but estimate only 17 of 93 files using translations (also reported as 18.3%), with 76 files pending and placeholder translations remaining. The achievement summary and progress report disagree on string counts. These are historical snapshots, not current coverage measurements.
- The i18n spec, plan and progress artifacts disagree on completion and targets. The plan gives both a less-than-50-KB bundle target and an earlier estimated 15-KB increase; the spec also refers to 100% translation coverage and no hardcoded French in scope. Do not treat the estimated bundle increase or planned rollout as measured results.
- The i18n plan’s missing-key behavior is inconsistent: its hook contract says a missing key errors in development, while a research example falls back to the key itself. The supplied records do not settle runtime behavior.
- The coverage records use different dates and phases. The July 2025 research projects about 82.3% for `my-asso` and 86.7% for `api-ae`; its plan estimates roughly 82% and 87%. Both projections are below their target. The May 2026 tasks say the initial test-fix work is complete but explicitly leave 90% coverage open. Do not treat the target as achieved.
- The coverage records exclude five complex or thin-wrapper `my-asso` files and boilerplate in `api-ae`, but the supplied digests do not name those files. The `api-ae` threshold set is 90% statements, lines and functions with 85% branches, even though the model document describes the projected total as approximately 87%. Confirm the actual Jest configuration before interpreting a percentage as compliance.
- A populated 032 specification dated 17 May 2026 concerns a green test suite; the separate plan and task records add a 90% coverage objective. The earlier `specs/032-unit-tests-coverage/spec.md` is an unfilled template. Use the populated `spec/spec.md` for suite health and the later plan/tasks for the coverage initiative, not the blank template.

- Which translation targets are release gates today: complete coverage and zero hardcoded French, or the progress-report baseline and incremental module rollout? Are the less-than-50-KB and less-than-5% performance limits measured anywhere?

- Is a composite index required for production scheduled-activation queries? The spec, research and tasks disagree; verify the exact query and deployed indexes before changing or deploying scheduling behavior.
- Should toggle creation initialize all three environment values explicitly to `false`, or can an unset map value continue to inherit legacy `isEnabled`? The task list specifies the former while backward-compatibility rules permit the latter.

- What are the exact files excluded from each coverage denominator, and is the enforceable `api-ae` aggregate target 90% or the approximately 87% projection? The records do not reconcile the projected figures with the thresholds.
