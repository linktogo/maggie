## What it does

This domain describes MyAsso's connections to external services and cloud-file providers, including Google Drive asset browsing, a planned Frama.space/Nextcloud integration, and the association-level Facebook and Instagram OAuth integration. It also includes a proposed general integrations hub. The design records place most of this work in `apps/my-asso`; Frama.space additionally proposes a reusable library under `libs/frama-space/`.

These documents are specifications and plans, not a verified inventory of deployed behavior. Their task lists report partial or contradictory progress, so check the current code and configuration before relying on any proposed path or capability.

## Architecture as designed

- **Google Drive assets:** Reuse the existing Google OAuth service and `user_tokens/{uid}` tokens, with `drive.file` and `drive.metadata.readonly` scopes. The planned `google-drive-asset-service.ts` and `DriveAssetContext` support file browsing, search, selection, permission warnings and previews; UI components include `DriveFileBrowser`, `DriveAssetPicker`, `DriveAssetPreview` and `DriveExcelViewer`. The specification proposes a `/drive-assets` page and selection integration in Blog, Events, Wiki, Communications and user profiles. Store Drive links rather than importing assets into Firebase Storage. (`specs/001-google-drive-assets-integration/spec/spec.md`; `specs/001-google-drive-assets-integration/spec/tasks.md`)
- **Frama.space / Nextcloud assets:** The proposed `libs/frama-space/` library contains WebDAV browsing, URL helpers, encryption, a React context and reusable UI. MyAsso is to provide provider routes, a page, and a unified picker alongside Google Drive. WebDAV is for file access and OCS for sharing; links point to Frama.space rather than importing files into Firebase Storage. The specification puts credentials on each user's profile and module activation on `AuthGroup`, but the later task record conflicts about where configuration belongs; see drift below. (`specs/025-frama-space-assets-integration/spec/spec.md`; `specs/025-frama-space-assets-integration/spec/plan.md`; `specs/025-frama-space-assets-integration/spec/tasks.md`)
- **Meta OAuth:** Each association brings its own Meta developer app. The OAuth connect, callback and status routes use `src/services/meta-service.ts`; configuration is intended to be managed in Admin > Auth Groups rather than the separate `/admin/social/meta` page. The 2026-07-17 plan adds a dedicated `src/app/actions/meta-actions.ts` for secret configuration, reuses the existing AES-256-GCM helpers, and encrypts the App Secret and access token with a per-group `metaEncryptionKey`. `meta-service.ts` decrypts credentials before Graph API use. Instagram detection searches Facebook pages for the first linked Instagram Business Account and falls back to the first Facebook page. (`docs/superpowers/specs/2026-07-17-meta-integration-fixes-design.md`; `docs/superpowers/plans/2026-07-17-meta-integration-fixes.md`)
- **General integrations hub:** `specs/021-integrations-tierces/spec/spec.md` proposes a marketplace/configuration/status interface and an `Integration` model for external services, including OAuth, encrypted API keys, token refresh and signed webhooks. It identifies HelloAsso, Google Drive and Twilio as existing integrations, but does not give their implementation paths or establish that the proposed generic hub exists.

## Invariants

1. Keep the Meta app credentials association-specific; do not introduce a centrally managed Linktogo Meta app as part of these changes. **Source:** `docs/superpowers/specs/2026-07-17-meta-integration-fixes-design.md`; `docs/superpowers/plans/2026-07-17-meta-integration-fixes.md`.
2. Do not store new Meta App Secrets or access tokens in plaintext. Continue to read legacy plaintext values through `decryptSecretSafe()`; do not add a bulk migration or backfill. Do not modify `src/lib/encryption.ts` or add a dependency for the planned fixes. **Source:** `docs/superpowers/specs/2026-07-17-meta-integration-fixes-design.md`; `docs/superpowers/plans/2026-07-17-meta-integration-fixes.md`.
3. Keep the Meta App ID and redirect URI plaintext; encrypt the App Secret and access token with the existing AES-256-GCM helpers, and use the per-group `metaEncryptionKey`. **Source:** `docs/superpowers/specs/2026-07-17-meta-integration-fixes-design.md`; `docs/superpowers/plans/2026-07-17-meta-integration-fixes.md`.
4. Keep Meta configuration writes on the dedicated server-side action, separate from generic client-side form saving. Under the later plan, rely on Firestore security rules for the admin check; verify those rules before changing this boundary. **Source:** `docs/superpowers/plans/2026-07-17-meta-integration-fixes.md`.
5. Do not add Meta publishing, event import, automatic token refresh or centralized-app support under the described fixes. Long-lived token expiry requires manual reconnection. **Source:** `docs/superpowers/specs/2026-07-17-meta-integration-fixes-design.md`; `docs/superpowers/plans/2026-07-17-meta-integration-fixes.md`.
6. For Google Drive, respect the provider's permissions; do not manage sharing or edit remote files. Warn about private files and let the user continue or cancel; do not force a file public. **Source:** `specs/001-google-drive-assets-integration/spec/spec.md`; `specs/001-google-drive-assets-integration/spec/tasks.md`.
7. Do not import Google Drive or Frama.space assets into Firebase Storage for these integrations; persist and use provider links. Do not add Drive↔Firebase synchronization, remote editing, file creation, sharing or permission management. **Source:** `specs/001-google-drive-assets-integration/spec/spec.md`; `specs/025-frama-space-assets-integration/spec/spec.md`.
8. Keep Drive navigation limited to the root and one subfolder, while allowing global name search; account for pagination beyond 50 files. Use the specified one-hour listing cache and invalidate it when Drive changes are detected. **Source:** `specs/001-google-drive-assets-integration/spec/spec.md`; `specs/001-google-drive-assets-integration/spec/tasks.md`.
9. Validate configurable Nextcloud server URLs, encrypt stored credentials, and never store or log a plaintext password. Keep Frama.space credentials user-specific unless the conflicting implementation record is resolved. **Source:** `specs/025-frama-space-assets-integration/spec/spec.md`; `specs/025-frama-space-assets-integration/spec/tasks.md`.
10. For the proposed general integrations hub, encrypt API keys, refresh OAuth refresh tokens when required, verify HMAC signatures on inbound webhooks, apply rate limiting and log calls. Treat this as proposed hub behavior, not proof that every integration implements it. **Source:** `specs/021-integrations-tierces/spec/spec.md`.

## Drift and superseded decisions

This is the risky part of the document: these sources mix a Google Drive feature specification and partially checked task list, Frama.space design and implementation tracking with conflicting details, a broad integrations proposal, and a Meta plan whose tasks are unchecked. None of those records alone proves the current code or deployed configuration.

- **Meta authorization differs between the approved design and the later plan.** The design spec says the dedicated Server Action should check that the user is an admin. The later implementation plan says to rely on Firestore security rules, following `saveDiscordConfig()`. The later plan is the current recorded choice, but check the actual action and rules together; do not assume the Firestore-only check is in place or equivalent to an application-level check.
- **Meta token encryption is resolved by the later plan.** The design spec leaves open whether encryption belongs in `meta-service.ts` or the OAuth callback. The plan chooses service-layer encryption: `saveMetaTokens()` encrypts and `getAllMetaData()` decrypts. Do not infer that the plan was implemented: its checklist is unchecked.
- **Meta config storage has a known false lead.** `/admin/social/meta` reads and writes a Firestore settings location the OAuth flow does not populate. The design and plan remove this ghost page and use Admin > Auth Groups; verify the current routes before changing configuration UI.
- **The Google Drive progress record is internally inconsistent.** `tasks.md` says “Not Started” while marking many tasks complete; it also leaves OAuth end-to-end verification, Blog selection integration, other module integrations, documentation, translations and E2E work open. Its task list says simple single-file selection, while `spec.md` says one or more files. The analysis recommends resolving this cardinality conflict, clarifying Excel iframe permissions, insertion formats and cache invalidation, and reconciling duplicate or malformed requirement text. Do not assume multi-select or complete integrations without checking.
- **Frama.space storage/configuration ownership is unresolved.** The specification and technical plan say credentials belong to each user's profile, with module activation on `AuthGroup`. The task list also says configuration is an admin interface using `updateAuthGroupSettings`, yet separately requires connection credentials in `UserProfile`. Its status reports substantial checked work but unfinished tests and documentation, conflicting locale checklists, and FIXME path aliases. Confirm the actual data model and which configuration is user-owned before changing it.
- **Frama.space routes and page location drift from the original proposal.** The spec proposes `/frama-assets`; later tasks refer to `/applications/frama-space`. The task record describes both an aggregate `/api/cloud/frama-space/` route and separate `/api/frama-space/*` routes. The plan's route and page proposals are not a single authoritative contract; inspect the implementation before extending either shape.
- **The general integrations hub is only a broad feature specification here.** `specs/021-integrations-tierces/spec/spec.md` says some integrations, including HelloAsso, Drive and Twilio, are already implemented, but supplies no paths, deployment status or shared-hub evidence. Do not infer a common runtime architecture or that all listed providers are connected.

## Open questions

- Which Google Drive task-list items shipped, and is the picker single-select or multi-select? Which modules currently consume it, and what exact link/embed representation does each consumer store?
- What is the current Google OAuth scope and refresh behavior in code? Have OAuth end-to-end tests, private-file permission checks, Excel preview checks and cache invalidation been verified?
- Which Frama.space credential source is authoritative: `UserProfile` per user, or settings written through `updateAuthGroupSettings`? How is association-level module activation kept distinct from an individual user's connection?
- Which Frama.space API route shape and page route are live? Are the library path aliases, Nextcloud 25–28 compatibility, cache, pagination and thumbnail fallback issues resolved?
- Does the Meta Server Action perform an application-level admin check, rely only on Firestore rules, or use both? What do the deployed rules enforce for this write?
- Have the Meta encryption and Instagram page-selection changes shipped? Does the diagnostic script run with the expected service account and Firebase environment, and has OAuth been verified manually in staging?
- For Meta, which configuration values are required to reconnect after a long-lived token expires, and what user-facing behavior communicates the need for manual reconnection?
- Does a generic integrations hub or `Integration` model exist in the current code? If so, which provider adapters and webhook routes actually use its proposed credential, logging, rate-limit and token-refresh contracts?
- The design records do not settle operational owners for rotating encryption keys or recovering credentials for Google Drive, Frama.space or Meta. Agree on ownership and recovery behavior before changing credential formats or key storage.
