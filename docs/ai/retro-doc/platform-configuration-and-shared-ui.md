## What it does

This domain provides the reusable foundations that make the application consistent across routes and modules: locale-aware navigation, theme and accent-color application, feature-toggle storage and resolution, and shared UI primitives for headers, status, empty, loading, dialog, table-action, KPI, filtering, and export patterns. The primary application code is under `apps/my-asso/src`, with reusable components and hooks in `libs/lk-ui`.

It also includes the application-shell behavior that is explicitly part of the shared experience: global breadcrumbs in `(main)/layout.tsx`, the mobile installation prompt in the main layout, and the four-locale translation files. The landing page has its own Angular implementation under `apps/landing-next`; mention it only where its header and locale-switcher decisions establish a separate shared-navigation pattern.

## Architecture as designed

- **Localization foundation.** `apps/my-asso/src/i18n/LocaleContext.tsx`, `config.ts`, `date-locale.ts`, and `locales/{fr,en,de,es}.json` provide the existing four-language system. Components call `useLocale()` and use `t()` with `{{variable}}` replacement. The design keeps this system rather than introducing `react-i18next`, `next-intl`, or FormatJS; automated scripts validate key parity, hardcoded French, and coverage.
- **Feature toggles.** `FeatureTogglesContext` reads and mutates tenant-scoped `feature_toggles` and immutable `feature_toggles_history` documents through the Firestore client SDK. The admin page is `/feature-toggles`, with `ToggleCard`, `ToggleDialog`, `HistoryDialog`, and `CredentialsDialog`. The context exposes CRUD, status changes, and history retrieval. Scheduled activation is handled by the `apps/blog-api/src/functions/feature-toggles.function.ts` Cloud Function.
- **Environment-aware toggle resolution.** Feature 031 extends toggles with optional `environments` and `scheduledActivations` for `dev`, `test`, and `prod`, while retaining `isEnabled`, `activationMode`, and `scheduledDate` as production/legacy mirrors. `resolveEnvState` is intended to be centralized in `apps/my-asso/src/lib/data.ts` and reused by the frontend context, Next.js routes, and `blog-api`. The Next.js `/api/feature-toggles/check` and `/list` routes and the `blog-api` GET endpoints return only the resolved state and requested environment.
- **Breadcrumb navigation.** The global breadcrumb is UI-only: `usePathname()` is parsed against a static route table in `apps/my-asso/src/lib/breadcrumb-config.ts`, translated through `useLocale()`, and rendered by `components/breadcrumb-nav.tsx` using shadcn/ui Breadcrumb primitives. It is mounted in `(main)/layout.tsx`, does not use Firebase or a feature flag, hides unknown dynamic identifiers, and collapses intermediate segments into a mobile `DropdownMenu`.
- **User theme color.** `UserColorContext` owns the per-user accent preference separately from light/dark `ThemeContext`. `apps/my-asso/src/lib/theme-colors.ts` defines eight typed colors with light/dark HSL variables. The provider applies CSS variables and localStorage immediately, then synchronizes `user_profiles/{uid}.themeColor` through the client SDK after authentication. The root layout's inline anti-FOUC script applies the cached color before rendering; `/profile` exposes the selector through an Apparence tab.
- **Shared component library.** `libs/lk-ui` is the reusable foundation. It exports `ConfirmDeleteDialog`, `PageHeader`, `StatusBadge`, `EmptyState`, `TableActionCell`, `KpiCard`, `CrudDialog`, `ExportButton`, `useFilteredData`, `useExportXlsx`, and the loading components under `libs/lk-ui/src/components/loading/`. These components are intentionally context-free where possible; callers supply translated text and domain-specific status maps, actions, persistence, and form state.
- **Application-shell installation behavior.** The mobile install prompt uses `src/hooks/use-device-type.ts`, `src/lib/pwa-install.ts`, `src/components/mobile-install-prompt.tsx`, `public/manifest.json`, and `scripts/generate-icons.js`. It is mounted from `src/app/(main)/layout.tsx`, supports native, iOS, and manual installation paths, and intentionally has no service worker.
- **Separate landing-page header pattern.** `apps/landing-next` uses standalone Angular components, including `header` and `locale-switcher`, with route-preserving locale navigation, an inline three-circle SVG logo, and custom listbox semantics. This is a separate deployed Angular application, not a replacement for the MyAsso locale or shell infrastructure.

## Drift and superseded decisions

This is the risky part of the document: the record combines approved designs, implementation plans, and task files that sometimes claim delivery while leaving validation or deployment open. The code remains authoritative.

- The original shared-component specifications place components under `apps/my-asso/src/components/shared`; the plans and task records later move them to `libs/lk-ui`. Treat `libs/lk-ui` as the current design, and verify imports before adding another app-local copy.
- The shared-component task records call the components delivered and tested, but several leave migrations, typecheck, lint, dependency verification, or Radix interaction tests open. Do not infer that every module already uses the shared primitives.
- Feature 025 first describes a public `blog-api` toggle API and a communication-area route; the later 19 March specification and plan place the admin page at `/feature-toggles`, use direct Firestore through `FeatureTogglesContext`, and defer the public endpoint. Treat the later decision as current.
- Feature 025’s implementation status says the code is implemented but Firebase indexes, rules, and the scheduled Cloud Function still need deployment; the task record likewise leaves i18n and deployment open. Verify deployed rules and functions before relying on scheduled toggles.
- Feature 031 is newer than the base toggle design and is marked in progress/planning rather than delivered. Its contracts and model are the current intended behavior, not proof that environment-aware state exists in production.
- The generic technical-analysis documents for breadcrumbs and user theme color propose Firestore collections, contexts, Server Actions, or feature flags. Those proposals are superseded by the UI-only breadcrumb model and the per-user `UserColorContext`/`user_profiles` model.
- The user-theme-color specification contains conflicting references to custom hexadecimal colors and `users/{uid}`. Later clarification, research, data model, contract, and plan select predefined colors and `user_profiles/{uid}`; do not implement free-form colors or a new user collection without a new decision.
- The i18n progress reports describe infrastructure and keys as complete while reporting only 17 of 93 main-space files translated and 18.3% file coverage. Shared UI work must not assume that all caller text is translated merely because locale files and validation scripts exist.
- The landing-next redesign and header-rework records are approved plans with unchecked implementation steps. They describe a separate Angular application and must not be treated as evidence that the MyAsso shell, locale switcher, or logo has changed.
- The mobile-install specification is marked done, but its deliberate omission of a service worker means the installed app remains network-dependent. Do not add offline assumptions to the prompt or manifest behavior.
