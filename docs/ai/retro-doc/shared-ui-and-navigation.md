## What it does

This domain records reusable interface components, list and export utilities, standardized loading patterns, and application-wide breadcrumb navigation for MyAsso. The component plans converge on `libs/lk-ui` as the shared package; the breadcrumb design is a separate MyAsso UI integration that derives navigation from the current pathname.

The records include specifications, implementation plans, and task reports. A task report that marks a component delivered is evidence of reported work, not proof that every proposed migration, verification step, or current runtime behavior is complete.

## Architecture as designed

- **Shared UI package:** `libs/lk-ui` holds reusable presentation components and the `useFilteredData` and `useExportXlsx` hooks, with public exports from the package barrel. Components that do not need client state are designed to work as React Server Components; `TableActionCell` is a client component because it wires up action handlers.
- **Reusable page and status presentation:** `PageHeader` standardizes a page title and optional description, badge and actions, while `StatusBadge` renders caller-supplied status configuration. Status meaning remains local to each domain rather than being centralized in the shared package.
- **Empty, loading and KPI presentation:** `EmptyState` covers inline, card and table empty results. The loading components provide a spinner, table and card skeletons, and `WithLoading` for conditional loading display. `KpiCard` presents a metric with optional navigation, loading, trend and description.
- **Dialogs and table actions:** `ConfirmDeleteDialog` standardizes destructive confirmation and loading feedback. `CrudDialog` supplies a dialog shell and sticky footer while callers own form state and fields. `TableActionCell` renders common view/edit/delete actions and configurable additional actions.
- **List and export utilities:** `useFilteredData` combines configured search, discrete/custom filters, sorting and counts over caller-provided records. `useExportXlsx` dynamically loads `xlsx` and exports caller-provided, already-filtered data as a single- or multi-sheet workbook; `ExportButton` exposes the loading-aware action.
- **Breadcrumb navigation:** `BreadcrumbNav` is planned for the `(main)` layout between the header and main content. It derives segments from `usePathname()`, translates route labels through `useLocale()` and static configuration, and uses the shared shadcn breadcrumb primitives. On narrow screens, intermediate segments move into a dropdown; the root route has no breadcrumb.
- **Localization:** Shared components accept caller-provided text rather than embedding translation hooks. The broader `(main)` translation records prescribe `LocaleContext`, `useLocale()` and `t()` for localized UI, with French as the source of truth and four aligned locale files (`fr`, `en`, `de`, `es`). The progress records report that source-level translation work remained incomplete.

## Invariants

1. Keep the shared UI package free of domain-specific status meanings: provide status mappings at the call site, and keep shared text configurable by callers. **Source:** `specs/033-confirm-delete-dialog/spec/spec.md`; `specs/034-page-header/spec/spec.md`; `specs/035-status-badge/spec/spec.md`.
2. Keep `PageHeader`, `StatusBadge`, `EmptyState`, `KpiCard`, and the loading components context-free and compatible with React Server Components; use client behavior only where interaction requires it, as with `TableActionCell`. **Source:** `specs/034-page-header/plan.md`; `specs/035-status-badge/plan.md`; `specs/036-empty-state/plan.md`; `specs/037-table-action-cell/plan.md`; `specs/038-kpi-card/plan.md`; `specs/042-loading-state/plan.md`.
3. For `StatusBadge`, render nothing for an empty status and use the configured fallback label or raw status for an unknown value. For `EmptyState`, preserve the default/card/table variants and render table content through table row and cell primitives with the supplied column span. **Source:** `specs/035-status-badge/spec/spec.md`; `specs/036-empty-state/spec/spec.md`.
4. In `TableActionCell`, use a link for a view URL, support hidden/disabled custom actions, and do not wrap the component in a second table cell. **Source:** `specs/037-table-action-cell/plan.md`; `specs/037-table-action-cell/spec/spec.md`.
5. In `useFilteredData`, treat `'all'` as no filter, combine active criteria, and perform case-insensitive search; nested dot-path search is optional in the specification. **Source:** `specs/039-use-filtered-data/plan.md`; `specs/039-use-filtered-data/spec/spec.md`.
6. In `CrudDialog`, keep the form state in the caller and the footer outside the scrollable body; do not assume complex adherents or formation forms must migrate to the shared dialog. **Source:** `specs/040-crud-dialog/plan.md`; `specs/040-crud-dialog/spec/spec.md`.
7. In `useExportXlsx`, let callers provide already-filtered records and column labels, support accessor functions and multiple sheets, and produce headers even for an empty dataset. The export button is disabled while exporting or when its data is empty. **Source:** `specs/041-use-export-xlsx/plan.md`; `specs/041-use-export-xlsx/spec/spec.md`.
8. For breadcrumbs, derive labels from static configuration and locale translations, keep parent segments navigable and the current segment non-clickable, and use accessible navigation/list semantics. Do not query Firestore or add a feature flag. **Source:** `specs/028-breadcrumb-navigation/spec/spec.md`; `specs/028-breadcrumb-navigation/research.md`; `specs/028-breadcrumb-navigation/spec/plan.md`.
9. Hide the breadcrumb on `/`; on mobile, replace intermediate segments with an ellipsis dropdown and close it when the pathname changes. **Source:** `specs/028-breadcrumb-navigation/spec/spec.md`; `specs/028-breadcrumb-navigation/spec/plan.md`.
10. Keep all four `(main)` locale files structurally aligned, with non-empty values and consistent interpolation variables; new localized components should use the existing `useLocale()`/`t()` pattern and add keys to every locale. **Source:** `specs/002-i18n-main-space-translation/spec/plan.md`; `specs/002-i18n-main-space-translation/spec/quickstart.md`; `specs/002-i18n-main-space-translation/spec/research.md`.

## Drift and superseded decisions

This is the risky part of the document: component specifications, implementation plans and later task reports do not agree on every path, feature detail or completion state. Treat the chosen designs below as design history, not as an assertion that all components or migrations are present in the current code.

- The component specifications often name `apps/my-asso/src/components/shared/` or `src/hooks/`, while later plans and task records place reusable components and hooks in `libs/lk-ui`. The latter is the recorded implementation location; check package exports and imports before using any older app-local path.
- The records describe migrations as delivered for some initial consumer pages, but repeatedly leave remaining migrations, type-check and lint open. The `CrudDialog` task report also leaves unit tests open because Radix dialog interactions need mocks. Do not infer repository-wide adoption or a passing quality gate from component delivery.
- `ConfirmDeleteDialog`'s spec describes controlled `open`, `onConfirm` and `onCancel` props; its task report says the delivered component supports controlled and uncontrolled modes. Verify the actual public API before extending it.
- `StatusBadge`'s plan lists four configurations, while the specification lists five, including formation. The task record reports migrations in four areas. Keep new domain status maps local and inspect current exports/usages rather than assuming every listed config shipped.
- The `CrudDialog` specification is marked Draft and requires successful submission to close automatically; the plan focuses on layout and caller-owned form behavior, while the task report records delivered open/close and submission handling but not tests. The spec also mentions a sheet variant not confirmed by the plan or task record.
- `useExportXlsx`'s task record reports the hook and button tested, but leaves confirmation of the runtime `xlsx` dependency and export migrations open. The spec and plan say to reuse the existing library; build-time availability is not established by the task report.
- Breadcrumb sources disagree on unknown URL segments. The research and plan say to treat unmapped segments as dynamic, use a generic parent-specific label where configured, and otherwise hide them. The specification also requests a readable transformation of untranslated segments. Prefer the detailed research/plan behavior for design intent, but inspect `parseBreadcrumbs` and its tests before changing fallback behavior.
- Breadcrumb `tasks.md` marks T001–T015 complete but leaves visual verification T016 open. Its status does not establish that the visual overflow criterion or all routes were checked.
- The `(main)` i18n reports describe completed extraction and locale-key tooling but only 17 of 93 files translated in one report, with hardcoded strings and placeholder translations still remaining. Reported string counts vary across the achievement summary and progress report, and the task checklist has inconsistent checkboxes and repeated IDs. Do not treat the translation effort as complete.
