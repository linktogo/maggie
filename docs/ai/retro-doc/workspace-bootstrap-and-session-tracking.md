## What it does

This domain bootstraps configured local repositories and tracks agent work in a workspace-level board. It selects or clones checkouts, installs dependencies when the repository has a supported manifest, and installs or reconciles local agent hooks. Hook events and explicit CLI actions update per-session board state; Claude Code and local GitHub Copilot CLI sessions share the same board and usage shape.

The design record places reusable behavior in `libs/workspace-bootstrap/` and workspace CLI dispatch in `apps/workspace/`. Hook settings live in each checkout, while board state and ended-session history live under the workspace directory. The board server starts reconciliation when given configuration, but it is not required for hooks or CLI commands to write state.

## Architecture as designed

- `apps/workspace/` owns CLI argument parsing and status routing. It supplies the workspace-level options and derives the hook command path from the app location.
- `libs/workspace-bootstrap/` contains checkout selection and bootstrap operations, installer planning, board state operations, token extraction, hook installation, and startup reconciliation.
- `libs/workspace-bootstrap/src/agents.js` is the agent registry: it selects settings locations, constructs hooks, detects drift, and installs hooks. Agent-specific hook behavior is separated into agent modules.
- `libs/config/src/config.js` accepts an optional string `path` for each repository. Bootstrap resolves it with `path.resolve(repo.path)`; otherwise it uses `<workspaceDir>/<repo.name>`. External checkouts share the board under `<workspaceDir>/.ai-sync/`.
- `libs/workspace-bootstrap/src/installers.js` selects the first matching installer: `package.json` selects pnpm before `pom.xml` selects Maven. The default is cache-first; `--offline` asks the package manager to use only its local cache.
- `libs/workspace-bootstrap/src/board.js` owns atomic board state updates and session lifecycle. Runtime board state is `board.json`; ended sessions are appended to sibling `history.jsonl`.
- `libs/workspace-bootstrap/src/hooks.js` and agent-specific hook modules construct and install local hook settings. Claude settings are in `.claude/settings.local.json`; Copilot settings are in `.github/copilot/settings.local.json`.
- `libs/workspace-bootstrap/src/reconcile.js` compares installed hook commands with current expected commands and returns a per-repository result. `apps/board/server.js` invokes reconciliation at startup only when configuration is supplied. It does not clone missing repositories or install dependencies.
- Claude and Copilot sessions are keyed by their agent session IDs in one version-2 board schema. The board server passes the data through; session grouping and transitions are handled in the client. Token usage is extracted by the bootstrap library, and the workspace CLI forwards lifecycle events and usage.

## Invariants

1. Resolve a checkout from `repo.path` when supplied; otherwise use `<workspaceDir>/<repo.name>`. Do not infer external paths or check their existence while parsing configuration. Source: `docs/superpowers/specs/2026-07-23-external-repo-path-design.md`; `docs/superpowers/plans/2026-07-23-external-repo-path.md`.
2. Keep the board in the workspace selected for the bootstrap invocation, including when a repository checkout is external. Derive worktree and reinstall/timestamp clone locations from the selected checkout's parent. Source: `docs/superpowers/specs/2026-07-23-external-repo-path-design.md`; `docs/superpowers/plans/2026-07-23-external-repo-path.md`.
3. Do not install dependencies during board-startup reconciliation, and do not clone or create missing checkouts there. Reconcile existing configured checkouts only. Source: `docs/superpowers/specs/2026-07-23-board-startup-hook-reconciliation-design.md`; `docs/superpowers/plans/2026-07-23-board-startup-hook-reconciliation.md`.
4. Continue reconciliation after an individual repository error, return a result for each repository, and seed the board with configured repository names after processing. Keep the server running if configuration loading or reconciliation fails. Source: `docs/superpowers/plans/2026-07-23-board-startup-hook-reconciliation.md`.
5. In the installer registry, check `package.json` before `pom.xml` and run no install when neither marker exists. Dry-run must not execute installs. Use pnpm `install --prefer-offline` by default and `install --offline` in strict mode; use Maven `dependency:go-offline` by default and `-o dependency:go-offline` in strict mode. Source: `docs/superpowers/specs/2026-06-21-local-offline-cache-design.md`; `docs/superpowers/plans/2026-06-21-local-offline-cache.md`.
6. Keep sessions separate by session ID within each repository. Use the fixed `manual` pseudo-session when a CLI status action has no session ID. Set a session title only from its first prompt; update `lastPrompt` on prompt submissions and preserve it when later events omit it. Source: `docs/superpowers/specs/2026-08-05-board-multi-session-cards-design.md`.
7. Remove a session on `SessionEnd` regardless of agent/source. A hard kill or crash without that event may leave stale state; do not treat the board as a permanent session ledger. Source: `docs/superpowers/specs/2026-08-05-board-multi-session-cards-design.md`.
8. Deduplicate Claude transcript assistant entries by `message.id`. Keep input, output, cache-creation, and cache-read usage separate; do not derive dollar cost in the bootstrap layer. Source: `docs/superpowers/specs/2026-08-07-board-token-usage-design.md`.
9. Treat unreadable transcripts as zeroed usage and skip malformed JSONL lines rather than failing the hook. Do not write history when no session record exists; on `SessionEnd`, prefer transcript usage when available and otherwise use stored usage. Source: `docs/superpowers/specs/2026-08-07-board-token-usage-design.md`.
10. For Copilot, use native camelCase event names and payloads while accepting normalized input key styles. Drain queued messages on `sessionStart` and `notification`; reserve hook stdout for JSON and send human-readable status to stderr. Source: `docs/superpowers/specs/2026-08-23-board-github-copilot-local-design.md`.
11. Treat Copilot's cumulative `modelMetrics` from `session.shutdown` as authoritative over accumulated per-turn usage. Map its cache token names into the shared board usage fields, and treat legacy null agent values as Claude. Source: `docs/superpowers/specs/2026-08-23-board-github-copilot-local-design.md`.
12. Keep manual session closure distinct from hook-driven `SessionEnd`: the UI close path records existing usage, or `null` if absent, without reading a transcript. A later hook may recreate a manually closed session. Source: `docs/superpowers/specs/2026-08-08-board-drag-to-done-design.md`; `docs/superpowers/plans/2026-08-08-board-drag-to-done.md`.

## Drift and superseded decisions

This is the risky part of the document: the record spans several revisions, and some plans describe proposed or partially checked work rather than verified current code. Treat the current design decisions below as intent, not proof that every path or behavior is present.

- The June 2026 board began with one status entry per repository and a version-1 schema. The August 5 multi-session design replaces that with version 2 and session maps. It deliberately resets old-shaped or malformed entries to `{ sessions: {} }` rather than migrating them; board data is considered disposable and hooks repopulate it.
- The original hook mapping used `UserPromptSubmit` for `inprogress`, and `Notification`/`Stop` for `question`; `done` was an explicit CLI status, not inferred from a hook. Later session designs remove sessions on `SessionEnd`, and describe `done` as a drop target rather than a persistent hook-set session status. Do not conflate “done” with the current session-close lifecycle.
- The August 7 implementation plan's transcript example sums assistant lines. The same-day design corrects this: deduplicate by unique `message.id`, since content-block lines may repeat one API response's usage. The design is the current rule.
- The original status design left open where to put Claude's instruction for explicitly marking `done`. The later supplied records do not resolve that placement.
- The early hook design names Claude's local settings. The August 23 Copilot design adds `.github/copilot/settings.local.json` and agent-specific behavior; reconciliation is then based on settings files present in each checkout, with Claude as fallback if neither agent's settings exists.
- Hook reconciliation's design pseudocode includes a `logger` option. Its implementation plan intentionally omits that option; the server logs from returned reconciliation results.
- The drag-to-done plan permits a later hook to make a manually closed session reappear. Manual close is a point-in-time override, not a tombstone.
- Completion evidence is uneven: the supplied reconciliation plan records targeted tests passing but also notes two known pre-existing board frontend failures; the external-path plan marks implementation and docs steps complete but leaves commit steps unchecked. The multi-session, token-usage, and drag-to-done plans have unchecked task lists, while the Copilot design is marked implemented. Do not infer completion of unchecked plan work from the design record alone.

## Open questions

- Where should the human-facing instruction for explicitly marking a session done live? The June board design suggested generated settings or a local notes file but left the choice unresolved.
- If a session ends via hard kill or crash and leaves a stale entry, should a future change add recovery or manual clearing? Current records explicitly accept stale sessions and exclude manual-clearing UI and crash recovery; ask before changing that lifecycle.
- Should old version-1 board data ever be migrated instead of reset? The multi-session design explicitly chooses reset for disposable runtime state; ask before introducing migration or preservation guarantees.
- When changing hook reconciliation or agent defaults, confirm whether the existing rule—reconcile from settings files, Claude fallback when neither is present—should remain, especially for partially configured or mixed-agent checkouts. The record does not describe all such cases.
- Before changing offline install guarantees, confirm whether cache misses may reach the network in the default mode. The design specifies soft cache-first by default and strict `--offline` as opt-in; Maven's `dependency:go-offline` may still miss artifacts needed by a later build.
- The supplied plans do not establish a consistent final implementation/test status for every session lifecycle feature. Before relying on plan checkboxes as current behavior, inspect the code and tests for the exact path being changed.
