# Skills library

A skill is written once and translated into each target platform's format. The
source of truth is `skills/<techno>/<name>/SKILL.md`; everything under a repo's
`.agents/`, `.claude/`, `.github/`, `.cursor/`, `.windsurf/` or `.maggie/` is
generated output, and so is the `maggie:begin skills` block of its `AGENTS.md`.

## What ships today

| Technology | Skills |
|---|---|
| `nestjs` | module structure, dependency injection |
| `postgres` | safe migrations, query performance |
| `nextjs` | App Router server/client boundaries |
| `reactjs` | component design, hooks |
| `angular` | component architecture, RxJS |
| `vuejs` | Composition API, state management |
| `nx` | monorepo structure, task running (affected + caching) |
| `firebase` | Firestore data modeling, Security Rules |
| `cloudflare` | Worker deployment (Wrangler, environments, secrets) |

## Authoring a skill

Create `skills/<techno>/<name>/SKILL.md` with YAML frontmatter followed by the
guidance body:

```markdown
---
name: nestjs-module-structure
description: Organize NestJS code into cohesive feature modules with clear public surfaces
globs: ["**/*.module.ts", "**/*.service.ts", "**/*.controller.ts"]
---

Keep one module per bounded context…
```

| Frontmatter | Required | Meaning |
|---|---|---|
| `name` | yes | Skill identifier; becomes the generated file name. Must be unique across the whole library, not just within a technology — by convention `<techno>-<directory>`, since it becomes the output path in every renderer. 1–64 lowercase letters, digits and single hyphens (the Agent Skills standard; `maggie lint` checks it). |
| `description` | yes | One line describing when the skill applies. At most 1024 characters. |
| `globs` | no | File patterns the skill is scoped to. Rendered differently per target — see below. |

Any repo whose `technologies` include `<techno>` picks the skill up on the next
sync. No registration step.

### Supporting files

A skill can ship more than its `SKILL.md`: scripts, reference documents, templates.
Put them in the skill's directory (`scripts/`, `references/`, `assets/`, or any
layout you like) and refer to them by their path relative to it:

```
skills/nestjs/module-structure/
├── SKILL.md
├── scripts/check-cycles.sh
└── references/module-boundaries.md
```

Every file in the directory is synced, except `SKILL.md` itself, dotfiles and the
`evals/` directory (see below). Directory formats (`claude`, `agents`) get them next
to the rendered `SKILL.md`, so relative paths keep working. Single-file formats
(`copilot`, `cursor`, `windsurf`) cannot hold them: they are written once under
`.maggie/skills/<name>/`, and the rendered rule ends with a *Supporting files*
section listing where they are.

### Evals

A skill's `evals/` directory holds cases that `maggie eval` runs to measure what the
skill changes — see [Skill evals](#skill-evals). It stays in the library: it is never
synced into a repository.

## How each target renders it

| Target | Output path | Frontmatter handling |
|---|---|---|
| `agents` | `.agents/skills/<name>/SKILL.md`, plus an index block in `AGENTS.md` | The [Agent Skills](https://agentskills.io) open standard, read by Codex, Gemini CLI, OpenCode, Goose and the other agents that follow it. Keeps `name` and `description`; drops `globs`. |
| `claude` | `.claude/skills/<name>/SKILL.md` | Keeps `name` and `description`; drops `globs`. |
| `copilot` | `.github/instructions/<name>.instructions.md` | Collapses `globs` into a single `applyTo` string, substituting `**` when absent. |
| `cursor` | `.cursor/rules/<name>.mdc` | Synthesises `alwaysApply` from whether globs exist; writes `globs: ''` for the empty case. |
| `windsurf` | `.windsurf/rules/<name>.md` | Plain markdown. |

The body survives verbatim across every target; frontmatter does not. That
asymmetry is why the canonical `SKILL.md` is the only file worth hand-editing —
a change made in a rendered file is lost on the next sync, and cannot be
reliably read back.

### The `AGENTS.md` index

The `agents` target also lists the repo's skills — name, link and description — in
`AGENTS.md`, the instructions file the agents of the standard read first. The list
is a managed block between two markers:

```markdown
# Team conventions          ← yours, never touched

Use pnpm.

<!-- maggie:begin skills — generated by maggie, edit the skills library instead -->
## Agent skills
…
<!-- maggie:end skills -->
```

A sync rewrites only what is between the markers, creates `AGENTS.md` when the repo
has none, and appends the block when the file has no markers yet. The block is
tracked in `.maggie/manifest.json` like the generated files: drop the `agents` target
and the next sync removes the block (and the file, if nothing else was in it).

## Linting the library

`maggie lint` checks every skill before it reaches a repository. A skill runs with
the agent's permissions in every repository it is synced to, so the library is
scanned like a dependency:

| Rule | Severity | Catches |
|---|---|---|
| `missing-skill-file` | error | a skill directory without a `SKILL.md` |
| `invalid-frontmatter` | error | frontmatter that does not parse, or misses `name` / `description` |
| `name-format` | error | a `name` that breaks the Agent Skills format (1–64 lowercase letters, digits, hyphens) |
| `description-length` | error | a description over 1024 characters |
| `duplicate-name` | error | two skills with the same `name` |
| `secret` | error | cloud keys, GitHub/Slack/OpenAI/Anthropic tokens, private keys |
| `pipe-to-shell` | error | `curl … \| sh`, `iwr … \| iex`, `base64 -d \| sh` |
| `prompt-injection` | error | "ignore previous instructions", "without telling the user"… |
| `hidden-unicode` | error | zero-width, bidirectional and tag characters that hide text from a reviewer |
| `credential-access` | warning | `~/.ssh`, `id_rsa`, `~/.aws/credentials`, `.netrc`, `.git-credentials` |
| `dangerous-command` | warning | `rm -rf /`, `--dangerously-skip-permissions`, `chmod 777`, force-push to main |
| `insecure-url` | warning | plain-`http://` (other than localhost) and raw-IP URLs |
| `html-comment` | warning | an HTML comment in a `SKILL.md` — invisible when the Markdown is rendered for review |

Supporting files are scanned too (binary files are skipped). The rules are
deterministic patterns: they catch the shapes of the published skill supply-chain
attacks, not every possible one, so they complement review rather than replace it.

```bash
maggie lint                 # exit 1 on an error
maggie lint --strict        # exit 1 on a warning too (what this repo's CI runs)
maggie lint --json          # machine-readable findings
maggie lint --skills ../my-skills
```

A legitimate match is silenced by naming its rule on the same line or the line
above — per rule, never blanket:

```markdown
<!-- maggie-lint-ignore pipe-to-shell -->
curl -fsSL https://bun.sh/install | bash
```

`maggie sync` runs the same lint first and refuses to touch any repository while the
library has an error (`--skip-lint` to bypass).

## Skill evals

A skill is only worth its context if it changes what the agent does. `maggie eval`
measures that: each case runs twice from the same starting checkout, once without
the skill (the baseline) and once with it rendered for the agent, and both runs are
graded by the same assertions.

A case is a JSON file in the skill's `evals/` directory:

```json
{
  "name": "orders-feature-module",
  "prompt": "Add an orders feature to this NestJS app: a GET /orders endpoint…",
  "fixture": "starter",
  "assert": [
    { "type": "file-exists", "path": "src/orders/orders.module.ts" },
    { "type": "file-contains", "path": "src/orders/orders.module.ts", "pattern": "@Module\\(" },
    { "type": "file-not-contains", "path": "src/orders/orders.controller.ts", "pattern": "\\[\\s*\\{" },
    { "type": "output-contains", "pattern": "orders" },
    { "type": "command", "run": "npx tsc --noEmit" }
  ]
}
```

| Field | Meaning |
|---|---|
| `prompt` | What the agent is asked to do. Required. |
| `fixture` | A directory inside `evals/` copied as the starting checkout. Empty directory when absent. |
| `assert` | Every assertion must hold for the run to pass. `pattern` is a regular expression. `command` runs in the checkout through the shell and must exit 0. |
| `name` | Shown in the report. Defaults to the file name. |

```bash
maggie eval --skill nestjs-module-structure            # Claude Code, one run per case
maggie eval --agent copilot --runs 5                   # every skill with evals, 5 runs each
maggie eval --skill nestjs-module-structure --json     # the full report
maggie eval --fail-on-regression                       # exit 1 if a skill makes things worse
```

```
nestjs-module-structure (claude-cli, 3 run(s) per case):
  orders-feature-module: 33% → 100% (+67 pts)
  overall: 33% without the skill → 100% with it: helps
```

Agents are non-deterministic: use `--runs` for a number worth acting on. A delta of
zero means the evals do not see the skill change anything — either the skill is not
needed for that task, or the cases do not test what it teaches. Other flags:
`--model`, `--timeout <seconds>` per run (default 600), `--work-dir`, and `--keep` to
leave the checkouts behind for inspection.

Evals run a real agent with edit rights in a temporary directory, and the commands
the cases name: they belong to the reviewed skills library, like the skills
themselves. The agent CLI (`claude` or `copilot`) must be installed and logged in.

## Technologies with no skills

A repo listing a technology with no `skills/<techno>/` directory — or that
otherwise resolves to zero skills — logs a warning and is left untouched.

Pass `--strict` to turn that into a hard error with a non-zero exit and the repo
recorded as `error`. Use it in CI to catch a typo'd technology or a skill folder
that was never created. See the [`maggie` CLI](sync-cli.md).
