# Generated-file marker in rendered skills — Design

**Date:** 2026-09-20
**Status:** Approved

## Purpose

This is P4 of [`docs/proposals/README.md`](../../proposals/README.md#p4--say-in-the-file-that-the-file-is-generated).

[`docs/skills-library.md`](../../skills-library.md) states that a change made
in a rendered file "is lost on the next sync, and cannot be reliably read
back." Nothing in the rendered file itself says so. All four renderers
([`libs/renderers/src/renderers/`](../../../libs/renderers/src/renderers/))
emit frontmatter plus the skill body verbatim, with no provenance of any
kind. Someone in a downstream repo can open `.cursor/rules/reactjs-hooks.mdc`,
see what looks like a normal rules file, improve it, and have the change
silently deleted on the next sync — by a tool they may never have heard of.

This design adds one line to every rendered file identifying it as
generated, where it came from, and where to make the real change instead.

## Decisions

- **No maggie version in the marker.** A version string would make the
  marker — and therefore the rendered file — change on every maggie release,
  even when the skill's own content is untouched. That means every skill file
  in every downstream repo would show as "changed" on the sync following any
  maggie release, for a reason with no bearing on the skill itself: pure
  noise in a sync PR's diff, and it works against future drift-detection
  tooling (a repo that's actually in sync would falsely read as needing a
  push). The marker only changes when the skill's source path changes
  (renamed or moved), which is a change worth surfacing.
- **The source path is the canonical convention path** —
  `skills/<techno>/<name>/SKILL.md` — not the literal filesystem path used
  for this run. The literal path can be an absolute, machine-specific
  location when maggie runs from a global install (the bundled library ships
  inside the installed package) or when `--skills <dir>` points somewhere
  project-specific. Neither is meaningful to someone reading the marker in a
  different repo. The canonical form is what every doc example already
  shows, is portable across machines and install modes, and is stable except
  when the skill genuinely moves.
- **Single insertion point.** All four renderers funnel their output through
  the shared `buildDocument(frontmatter, body)` helper in
  `libs/renderers/src/frontmatter.js`. The marker is added there, once,
  rather than in each of the four renderer files — `buildDocument` is
  internal to the `@linktogo/maggie-renderers` package (not part of its
  published `main` export, which is only `getRenderer`/`knownTargets`), so
  widening its signature is not a breaking change for consumers of the
  package.
- **`parseSkill`'s existing `source` parameter is untouched.** It already
  takes a `source` argument, but that one is the actual resolved path used
  only for error messages ("`${source}: skill frontmatter missing "name"`")
  — not necessarily the canonical form, and not attached to the returned
  skill object today. Rather than overload that parameter with a second
  meaning, `resolveSkills` (which already knows `techno` and the skill's
  directory name at the point it calls `parseSkill`) attaches the canonical
  path as a new `source` property directly on the returned skill object,
  after parsing. `skill.js` itself does not change.
- **HTML comment syntax**, consistent with the original proposal: no target
  platform's frontmatter or body parser chokes on it. It does still become
  part of what an agent reads in every downstream session — the marker is
  one line for exactly that reason.

## Marker format

```
<!-- Generated by maggie from skills/reactjs/hooks/SKILL.md — edit there, not here. -->
```

Placed as the first line of the body, after the frontmatter's trailing blank
line and before the skill's own content — so it's the first thing a reader
(human or agent) sees after the frontmatter.

## Data flow

```
resolveSkills (skills.js)
  parseSkill(content, skillFile)          — unchanged, returns {name, description, globs, body}
  skill.source = `skills/${techno}/${entry.name}/SKILL.md`   — new
  byName.set(skill.name, { skill, techno })

renderer.render(skill)                     — claude.js / copilot.js / cursor.js / windsurf.js
  buildDocument(frontmatter, skill.body, skill.source)        — new third argument

buildDocument(frontmatter, body, source)    — frontmatter.js
  `${serializeFrontmatter(frontmatter)}\n<!-- Generated by maggie from ${source} — edit there, not here. -->\n\n${body.trim()}\n`
```

`serializeFrontmatter` is unchanged.

## Files touched

- `libs/renderers/src/frontmatter.js` — `buildDocument` gains a required
  third parameter, `source`, and emits the marker line.
- `libs/renderers/src/renderers/claude.js`, `copilot.js`, `cursor.js`,
  `windsurf.js` — each passes `skill.source` as the new third argument.
- `libs/renderers/test/frontmatter.test.js` — updated for the new parameter
  and marker line.
- `libs/renderers/test/renderers/{claude,copilot,cursor,windsurf}.test.js` —
  each test fixture skill gains a `source` field, and expected `content`
  strings include the marker line.
- `libs/skill-sync/src/skills.js` — `resolveSkills` attaches `skill.source`
  after `parseSkill` returns.
- `libs/skill-sync/test/skills.test.js` — existing assertions extended (or a
  new one added) to confirm a resolved skill carries the expected `source`.
- `libs/skill-sync/test/pipeline.test.js` — the shared `skill` fixture
  (`{ name: 's', description: 'D', body: '# B' }`, used by five tests) gains
  `source: 'skills/nestjs/s/SKILL.md'`. Found while designing this feature,
  not part of the original request: without it, the "full run" test's
  rendered file would silently embed the literal text `undefined` in the
  marker. This never happens in production (`resolveSkills` always attaches
  `source`), but the test fixture should reflect that reality rather than a
  case that can't occur.

## Expected one-time effect

The sync immediately after this ships will show every rendered file in
every configured repo as changed, in every downstream repo — a large diff
whose entire content is "one line added," with no skill guidance actually
different. Worth a callout in release notes so it isn't mistaken for
unrelated skill churn when a maintainer reviews the sync PR.

## Out of scope

- Putting provenance in frontmatter instead of the body: rejected in the
  original proposal, since Claude and Copilot renderers strip unknown
  frontmatter keys they don't declare, while Cursor and Windsurf mostly
  don't — the marker would only reliably reach two of the four targets.
- A richer marker (e.g. naming the technology, or listing every target this
  skill also renders to): out of scope — the goal is provenance and a
  pointer to fix it at the source, in the fewest tokens that costs every
  future session reading it.
